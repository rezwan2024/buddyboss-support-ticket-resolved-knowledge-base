## Debugging steps
1. Loaded the same pages with Query Monitor and filtered Database Queries by component (Plugin: buddyboss-platform). BuddyBoss was about a sixth of the total on a clean admin account; WP Offload Media, Elementor, Paid Memberships Pro, LearnDash and WooCommerce added the rest, and most duplicate queries came from WP Offload Media repeating the same attachment lookup.
2. Query Monitor showed no persistent object cache in use: Redis was installed on the server (and enabled in the hosting panel) but WordPress was not connected to it, because the wp-content/object-cache.php drop-in was missing.
3. Compared the customer's account with the support account on the same pages: BuddyBoss queries were about 4 times higher on the customer's account, which had 73 unread notifications. The header notification menu loads every unread notification and the member, group or activity item behind each, about ten queries per unread notification.
4. Traced the remaining BuddyBoss queries on pages with no community content (at-mentions autocomplete list primed on every page, activity script setup pulling group data, table existence checks repeating each request) and logged them internally as performance improvements.
5. Ruled out: a code snippet to remove BuddyBoss queries on the cart page, since most of them come from the header notification menu itself.

## Solution
Connect WordPress to the server's Redis with a Redis object cache plugin (or ask the host) so the object-cache.php drop-in is in place, then mark all notifications as read on the heavy accounts and measure the pages again with Query Monitor.
Root cause: no persistent object cache in WordPress plus many unread notifications loaded in the header on every page, multiplied by other plugins' queries.
