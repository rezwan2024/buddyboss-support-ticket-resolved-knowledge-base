## Debugging steps
1. Reproduced on iOS: fully quit the app, cold launch and log in as a user with about 250 message threads. The app sends one POST /wp-json/buddyboss/v1/pusher/auth per thread right away, plus one for the user channel and one for the presence channel.
2. Server logs of the request bodies showed the same socket_id on every request and a different channel_name on each one. Ruled out: a reconnect loop or a retry loop.
3. The number of requests matches the thread count (threads + 2). Users with 50 to 100 threads get a shorter burst and rarely see a stall.
4. Each auth request loads WordPress fully. Other BuddyBoss endpoints (groups, members, activity) took 12 to 14 seconds during the burst and under 1 second after it.
5. Ruled out: server limits. Static files and the homepage stayed fast, there were no 502/504 errors and the object cache was active. Requests were waiting for a free PHP-FPM worker.
6. Support asked for a screen recording of the launch so the app team could match it to the request burst.

## Solution
No fix was confirmed in the ticket. As a workaround, the site added a web server rate limit with a large burst and a delay on the /wp-json/buddyboss/v1/pusher/auth endpoint. This spreads out the requests instead of rejecting them. Users with more threads than the burst size can get 429 responses and lose live-message updates on some threads.
Root cause: the app subscribes to and authenticates every message-thread Pusher channel at launch, so the number of requests grows with the size of the user's inbox.

## Customer note
Sent full reproduction steps and server findings and asked for the app team's timeline. No reply after support asked for a screen recording, and the ticket was closed for inactivity.
