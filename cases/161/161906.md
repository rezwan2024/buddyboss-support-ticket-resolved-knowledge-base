## Debugging steps
1. Traced the error call chain: admin_init > BB_DRM_Registry::run_addon_drm_check() > cleanup_addon_drm() > BB_DRM_Event::latest().
2. Checked the DRM installer: the table is created once when DRM first loads (since 2.16.0), then the option bb_drm_db_version is saved as 1.0.0 and creation is never retried.
3. Found that before 3.0.0 the unique index used 191 character prefixes, over the MyISAM 1000 byte limit with utf8mb4, so table creation failed on MyISAM default servers while the option was still saved.
4. Confirm on an affected site: SHOW VARIABLES LIKE 'default_storage_engine'; and check bb_drm_db_version is 1.0.0 in wp_options.

## Solution
On a current Platform version (3.0.0 or later), reset the installer: `wp option delete bb_drm_db_version`, open any wp-admin page once, then confirm with `wp db query "SHOW TABLES LIKE 'wp_bb_drm_events'"`. This creates the table with the correct schema and moves older DRM entries from wp_options into it; no manual SQL or other tables are needed. Calling BB_DRM_Event::create_table() directly also works but skips that migration step.
Root cause: initial table creation failed on MyISAM servers due to the old 191 character index prefix, and the saved version option stopped later updates from retrying.
