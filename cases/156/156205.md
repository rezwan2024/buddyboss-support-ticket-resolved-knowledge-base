## Debugging steps
1. Created a new account from the front-end registration page in a clean browser, activated and logged in: no password text in the name, could not reproduce.
2. Ruled out: the stored password. The customer changed the account password and the old value still showed in the name, and WordPress keeps passwords only as a one-way hash, so the value is plain text sitting in a name or profile field.
3. Likely cause: browser or password manager autofill put the password into the name input on the registration form, which only happens in a browser that already has a saved login for the site.
4. Planned checks with admin access: the WordPress user record (first name, last name, nickname, display name), the BuddyBoss extended profile Name field, user meta, the original signup record (it keeps the profile values as submitted) and a field-by-field compare with a clean test account.

## Solution
No final fix: the working admin access needed to check the user, profile and signup records was never provided, and the ticket closed for inactivity. Next steps were to find the field holding the value in the signup record, clear it from the affected profile field and review the registration form autofill behaviour.
Root cause: not confirmed; most likely browser or password manager autofill placing the password into a name field at registration.
