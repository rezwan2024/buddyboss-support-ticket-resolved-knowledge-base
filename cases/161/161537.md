## Debugging steps
1. Stack trace shows bp_nouveau_search_enqueue_scripts() running on login_enqueue_scripts from the Kadence Security login_header() screen.
2. Ruled out: a normal login with Forums, Network Search and Kadence two-factor on a test site loads fine.
3. Found the file defining bp_is_search_post_type_enable() loads on the WordPress init hook; WPO365 signs the user in on init before it, so Kadence renders its two-factor screen before BuddyBoss search settings exist.
4. Reproduced on a copy of the setup with a request copying the WPO365 timing: error without the snippet, gone with it.

## Solution
Add this PHP snippet in a code snippet plugin, set to run everywhere. It skips the BuddyBoss search script only when the search settings are not loaded yet (the early two-factor screen has no search box):
```php
add_action( 'bp_nouveau_enqueue_scripts', function () {
	if ( ! function_exists( 'bp_is_search_post_type_enable' ) ) {
		remove_action( 'bp_nouveau_enqueue_scripts', 'bp_nouveau_search_enqueue_scripts' );
	}
}, 0 );
```
The extra Kadence two-factor prompt after a Microsoft login is Kadence behavior, not BuddyBoss; skip the Kadence step for SSO logins if it is not wanted.
Root cause: in the Forums block, bp_nouveau_search_enqueue_scripts() calls bp_is_search_post_type_enable() without a function_exists() check, and login screens shown before init do not have it loaded.

## Customer note
Confirmed the error was gone with the snippet, kept their own workaround to skip Kadence 2FA for SSO, and thanked the team.
