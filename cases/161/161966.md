## Debugging steps
1. Created a regular member with a WordPress Application Password and added them to a hidden group.
2. Called the BuddyBoss REST groups endpoint for that hidden group with HTTP Basic auth: 403 instead of 200.
3. Checked inside the REST callback: get_current_user_id() returned the right user, but bp_loggedin_user_id() returned 0.
4. Found the same 403 on own "Only Me" xprofile fields, moderation report, promoting a group admin and self-deletion.
5. Found the groups list returned all hidden groups, including ones the member did not belong to, because the hidden-group filter is skipped when the user is logged in but the BuddyBoss user ID is 0.

## Solution
Update to BuddyBoss Platform 3.6.2 and Platform Pro 3.3.4 (also Sharing 2.1.1 and BuddyBoss Addons 1.2.3 if used).
Workaround before updating, added with a code snippet plugin, so Application Passwords are checked early on REST requests:
```php
add_filter( 'application_password_is_api_request', static function ( $is_api ) {
    $path = (string) parse_url( $_SERVER['REQUEST_URI'] ?? '', PHP_URL_PATH );
    return $is_api || str_starts_with( $path, '/' . rest_get_url_prefix() . '/' );
} );
```
Root cause: BuddyBoss cached the logged-in user at bp_setup_globals, before WordPress validated the Application Password, and never refreshed it when the REST server re-authenticated the user.

No reply after the fix release notice. The customer had shared the workaround and said it fixed all cases in their tests.
