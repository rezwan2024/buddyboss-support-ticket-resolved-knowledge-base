## Debugging steps
1. Read the stack trace: the fatal happens while the Plugins page builds its list and WordPress checks forced auto-updates through the auto_update_plugin filter.
2. WordPress starts that filter with a null value, but the trace shows the Platform update handler receiving the text "no", so another callback earlier on the same filter changed it.
3. Activate and deactivate both redirect back to the Plugins page, which is why every plugin action seems broken.
4. Asked for admin and SFTP access to find the plugin, must-use plugin or snippet that returns "no" on auto_update_plugin.

## Solution
Find the code that hooks auto_update_plugin and returns a string such as "no" (often an update manager, security plugin, host-added must-use plugin or a custom snippet). Disable it, or change it to return true, false or null. Rename its folder over SFTP or File Manager if the Plugins page will not load.
Root cause: a third-party callback on auto_update_plugin returns a string instead of a boolean, and the Platform update handler's strict ?bool return type throws a fatal error.
